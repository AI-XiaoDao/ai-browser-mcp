火山语法处理（两个脚本一致，逐条对应任务书要求）：

1. `@` 开头的行 = 内嵌 C++ 原文，**整行跳过**（本项目共 298 行），其 `{`/`}` 不参与计数。
2. `#` / `//` / `'` 开头的整行视为注释跳过（本项目共 1,905 行）。
3. 先对字符串字面量做**掩码**（保护 `\"` 转义），再剥行内 `//` 注释 →

4. 花括号块的“头行”若为 `参数 ...`、或为多行方法头的续行（`注释 = "..." @输出名 = ...>`），

### 1.2 判定规则（关键：区分“分支内返回”与“同级返回”）

- 只有当一个 `返回`/`跳出循环`/`继续循环`/`到循环尾` 是**某花括号容器的直接子级叶子语句**时，
  才把该容器内**其后的全部兄弟语句**判为不可达。
- `如果 (…) { … 返回 … }` 里的 `返回`，其直接父容器是**那个如果块**，
  所以“分支之后的同级语句”不受影响 → **不判死代码**（符合任务书要求）。
- `否则` 行被视为分支续接：一旦在死区中遇到 `否则`，探测立即撤销该死区。
  这是**结构性免疫**——正常的 `否则` 分支不可能被误报（实测撤销次数 = 0，即从未触发）。

## B. 仅脚本候选 / 我存疑的（0 处）

**探测 B 的实测结果：0 处。**

探测 B（“`如果/否则` 穷尽链、每个分支都以 `返回` 收尾 → 链之后的同级语句不可达”）
在全仓只找到 12 条符合“穷尽 + 全分支返回”的链，但**这 12 条链之后都没有任何同级语句**

这类“分支内返回导致不可达”的结构，按任务书要求**不属于**要报告的范围（任务书明确说分支内返回不算死代码），
故我既不放 A，也没有可放的 B。

需要额外说明：**40 处表面相似的候选被我主动排除**了——
如果只要求“全分支返回”而不要求链尾是**兜底 `否则`**（即 `如果 (甲) { 返回 } 否则 (乙) { 返回 }` 这种没有 catch-all 的链），
条件是**不穷尽**的：条件都不满足时会掉到链后语句，那些语句仍然可达。
去掉“链尾必须是兜底 `否则`”这条约束后，B 的候选从 12 激增至 52，其中 40 处都是这种伪候选。
这类结构就是本次探测里我最警惕的误判来源，也是我把 B 判据收得更紧的原因。

### B-1 探测器已知的能力边界（我会怀疑自己的地方）

1. **死区内部更深一层的“再次死区”被抑制。**
   如果一个容器已经被判死，它内部嵌套块里若还另有一个“无条件返回 + 后续兄弟”，
   我的实现只在最外层报一次（内层标为 `inherited_dead` 不再单独报）。
   本报告 A-1/A-2 里，容器内部那个 `如果 (vip_ctrl.是否为空 () == 假)` 块整体在死区内，
   属于这种情况；死区清单里已把它的内文逐行列全，所以**没有遗漏内容，只是没有单独计数**。
2. **多行“方法头”会打乱方法名归属。**
   实测 `MCP_Stdio.wsv` 的方法定义横跨 L327–L329（`方法 … 注释 = "…"` 折行）。
   我的回溯规则最初把该块误标为 `unknown`；修正回溯规则后方法数由 503 变为 504。
   这会影响“方法名”标注与统计，但**不影响死代码判定本身**（块仍然被建成容器）。
   此处修正后诊断已归零，但我不能排除还有别的罕见分行写法。
3. **`#` 开头行的定性。** 任务书只提到 `'` 与 `//` 是注释，但本仓大量使用 `# …` 作为整行文档注释
   （如 `MCP_Server.wsv` L2391 `# 存储格式为 {success,message,cdpEvent} …`）。
   我按注释处理（否则那 41 行含花括号的 `#` 行会直接崩坏括号层级）。
   若某些 `#` 行其实是可执行代码，我的层级会错——但 16 个文件括号全配平，没有支持“`#` 是代码”的证据。
4. **`跳出循环` / `继续循环` / `到循环尾` 的语义假设。**
   我把它们当作“无条件离开当前循环体”，即其后的同级语句不可达。
   全仓这三个关键字共出现 55 + 1 + 18 次，但**没有一处构成“无条件跳转 + 同级后续语句”**
   （它们全都写在 `如果 (…) { … }` 分支里），所以本次 A 清单里没有这类条目。
   若火山某变体允许 `跳出循环` 带层数参数跳到外层循环，我的“同层容器”模型仍然成立，但语义描述需修正。
5. **这是纯静态、纯语法级的探测，不是编译期可达性分析。**
   我只依据语法结构判定“同一容器内不可达”。我**没有**做：调用图分析（方法是否被调用）、
   常量折叠（`如果 (假)`）、异常/线程提前退出等分析。
   例如 A-1/A-2 所在的 `分类分派_核心操作` 我单独 grep 确认过是被调用的活方法
   （`MCP_Server.wsv` L10361 / L10366 / L10404 三处调用），所以那两处死代码是货真价实的不可达。
6. **未做跨文件/重复定义去重。** `MCP_Server.wsv`(253 个方法) 与 `MCP_Server_Core.wsv`(1 个大分派方法)
   看起来存在功能重叠；我按要求只扫 `src\*.wsv` 的 16 个正式文件，
   并**主动跳过** 6 个 `*_1.~vbak.wsv` / `*_2.~vbak.wsv` 备份（按技能规范，备份文件不参与审计）。
   如果你希望连备份一起扫，我可以补跑（但备份里的死代码无维护价值）。
