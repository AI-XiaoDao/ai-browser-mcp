### 1.7 **类库缺失接口清单 —— "硬阻塞"的准确定位**

在 `FBroLib.wsv` 中对 `类_FBrowser_菜单模式`（3288-3624）逐行核对，**不存在**以下接口（对照 CEF `CefMenuModel` 上游语义，**推断**依据：CEF 标准 API 命名约定 + 类库已暴露的同族 `*At` 方法命名风格）：

| 缺失接口（上游语义） | 后果（本方案中被阻塞的能力） |
|---|---|
| `GetLabelAt(index)` | 无法按索引读标签 → **无法枚举菜单文字** |
| `GetCommandIdAt(index)` | 无法按索引取命令ID → **无法枚举命令ID** |
| `GetTypeAt(index)` | 无法按索引读条目类型 |
| `GetGroupIdAt(index)` | 无法按索引读单选项分组 |
| `IsVisibleAt(index)` / `IsEnabledAt(index)` / `IsCheckedAt(index)` | 无法按索引读可见 / 可用 / 勾选态 |
| `GetSubMenuAt(index)` / `IsSubMenu(index)` | 无法按索引判定"这是不是子菜单" |
| `GetIndexOf(command_id)` | **无法把命令ID 与索引互相映射**（致命：导致"按索引读到的东西"与"按命令ID 读到的东西"是**两套互不相通的事实**） |
| `RemoveAt(index)` / `InsertItemAt` / `InsertSeparatorAt` / `SetLabelAt` / `SetTypeAt` / `SetGroupIdAt` | 无法按索引增删/改标签/改类型/改分组 |

**额外证据：`取菜单标签` 的签名不完整，不能当回读面用。**
原文照抄（`FBroLib.wsv:3371-3376`）：

```
    方法 取菜单标签 <公开 类型 = 文本型 注释 = "英文名：GetMisspelledWord" @禁止流程检查 = 真>
    {
        @ if(IsEmpty()) return CVolString();
        @ CefRefPtr<FBroString> fbrostring = FBroHsMenuModel_GetLable(m_class);
        @ return FBroUnit::FBroStringToCWString(fbrostring);
    }
```

三点异常：
1. **它没有任何参数** —— 而同族写方法 `置菜单标签`（3378）却接收 `命令ID`。一个"取标签"却没有"取谁的标签"的入参，语义不可确定；
2. 注释里的英文名写成 `GetMisspelledWord`（是从 `菜单环境.取错误单词` 复制过来的粘贴错误）；
3. 原生调用 `FBroHsMenuModel_GetLable(m_class)` 只传模型（对比 `FBroHsMenuModel_SetLable(m_class, id, label)`，`FBroLib.wsv:3382`），**不属于"按命令ID 取值"的形态**。

→ **结论：在未实测前，`取菜单标签` 绝不能作为"标签回读面"使用。** 本方案把它归入"确实做不到"，并在返回里点名它。

**还有一条更隐蔽的阻塞**：CEF 明确禁止在回调之外持有 `CefMenuModel` 引用（项目源码已记录此约束：`MCP_BrowserEvents.wsv:2854-2855` 注释「`菜单模式` 只在本次回调内有效(CEF 头逐字禁止回调外持引用)」）。这意味着**任何"读菜单"的能力都必须发生在回调内**，工具的 API 只能是"布下观察 → 触发右键 → 取回快照"两段式，**不可能**做到 `get_menu()` 这样的一次同步调用。

## 3. 可实施方案：可以做成工具且**能回读验证**的能力

> 总体形态约束（§1.7 末）：菜单模型只在回调内可见 → **一切菜单读取工具必须是"布观察 → 触发右键 → 取快照"三段式**。下面所有方案都遵守这一点。

### A1. `browser_menu_probe` —— 只读探针（**首要交付**）

**为什么必须有**：这是唯一能在**零写入**前提下回答"默认右键菜单长什么样（在可读范围内）"的工具。它补掉 §2.4 缺口 B/C。

**参数 schema 草案**

```json
  "y":           整数,
  "wait_ms":     整数,   // 默认 3000，上限 15000（arm/auto 时等待回调的毫秒数）
  "max_index":   整数,   // 默认 64，上限 256（索引扫描上限，防超大菜单拖死回调）
  "fields":      "count,accel,color",        // 默认 "count,accel"；color 会显著增加耗时
  "command_ids": "100,101,113,back,copy",    // 可选：额外按命令ID 探针（支持 §2.5 别名表）
  "color_types": "0,1,2,3,4,5",              // 可选，缺省全部 6 种（不含 计数=6）
```

**返回值草案（诚实分级）**

- 新增静态变量（紧邻既有菜单变量，`MCP_Server.wsv:361-378` 区块）：`是否观察菜单`、`菜单快照JSON`、`菜单快照序号`、`菜单快照时刻`、`菜单快照浏览器ID`、`菜单快照URL`、`菜单快照是否等到`。

- **回调挂钩**：`MCP_BrowserEvents.wsv:2842` `浏览器_即将打开菜单` 内、**既有 `如果 (MCP命令服务器.菜单已启用)` 之前**插入：
  ```
  如果 (MCP命令服务器.是否观察菜单)
  {
      MCP命令服务器.探针菜单模型 (菜单模式, 浏览器)   // ← 只读: 仅 取数量/存在快捷键_索引/取快捷键_索引/取颜色_索引

  ```
  ⚠ 顺序很关键：必须放在 `应用菜单规格` **之前**，否则探针读到的是"本服务刚改过"的模型，而非浏览器默认菜单。

### A2. `browser_menu_alias` —— 命令ID ↔ 别名双向解析（纯计算，不碰浏览器）

**为什么**：主代理明确要求"按已知命令ID别名表把命令ID翻成名字"。这是**唯一可以做到 100% 回读验证**的菜单相关能力（因为它是纯函数）。

**参数 schema 草案**
```json
{ "action": "list | to_id | to_name",
  "name":        "back",     // action=to_id
  "command_id":  113,        // action=to_name
  "include_standard_unknown": false }
```

**返回值草案**
```json
{ "success": true, "action": "to_name", "command_id": 113, "alias": "copy", "label_zh": "复制",
  "id_range": "cef_standard",         // cef_standard | service_custom(26500..28500) | 未知
  "source_of_truth": "MCP_Server.wsv 方法 解析菜单命令ID (快照行 8906) + CEF 标准 cef_menu_id_t",
  "caveat": "该表是 CEF 标准菜单项ID, 不是本应用菜单的真实内容; 实测(项目记录 MCP_Server.wsv:3091/8774)指向默认项的修改类不会生效, 别名只有标识/诊断价值" }
```

**回读验证怎么做**
- 纯函数 `自检`：`action=list` 输出整表 → 服务端启动期（或首次调用时）对每一项做 `to_id(to_name(x)) == x` 与 `to_name(to_id(x)) == x` 往返，往返失败则该项**不进表**并在 `self_check_failures` 里列出。

### A3. 既有 `browser_context_menu` 规格语法扩展：**按索引**修改类

**为什么并入而不新造工具**：这是"不能重复造轮子"的核心判断。按索引写（`选中状态_索引`/`设置快捷键_索引`/`移除快捷键_索引`/`置颜色_索引`/`置字体_索引`）需要"在回调内对活模型操作" —— 而既有 `browser_context_menu` 的 `set` 已经完整实现了"暂存规格 → 回调内施加 → 回读核对"的整套机件与状态字段（`菜单规格文本`/`菜单施加失败`/`菜单回读确认条数`/`菜单回读不一致`，`MCP_Server.wsv:361-377`）。新起一个平行工具会产生**第二个菜单状态机**，两边互相覆盖，是明确的负收益。

```
checkat||9|1|0|
```
⚠ **必须与既有"命令ID 列"区分开**：建议第 1 列名带 `at` 后缀做唯一判据（加进 `是菜单修改类` 的兄弟判定 `是菜单索引类`），并在 `MCP_Server_Core.wsv` 的参数校验里拒绝"`at` 类型却填了 26500..28500 这种明显是命令ID 的值"（既有代码已有同类错位守卫，见快照 3116-3128 的"列位固定"报错文案），报错文案要直接说"第 3 列是**索引**不是命令ID"。

**回读验证怎么做**：完全复用既有机制 —— 在 `应用菜单规格`（9034）内对每个 `at` 类型：先 `存在快捷键_索引(索引)`，写，再读回比对，一致才 `回读条数 + 1`，不一致写进 `菜单回读不一致`（既有格式 `[vis 26501 期望可见 实际相反] `）。`action=get` 已经把这些字段吐出来了（`MCP_Server_Core.wsv` 该分支的 `verified_items` / `verify_mismatch` / `apply_failed`）。

**落点**：`是菜单修改类`(8885) 旁新增 `是菜单索引类`；`应用菜单规格`(9034) 加分支；`MCP_Server_Core.wsv:3014` 参数校验加 `at` 类型与索引范围守卫。

### A4. 既有 `browser_context_menu` 规格语法扩展：`wipe` 行（清空菜单）

**为什么叫 `wipe` 而不叫 `clear`**：⚠ 既有工具**已经有** `action=clear`，其语义是"**撤销服务端预置的规格**"（`MCP_Server_Core.wsv` 该分支：清空 `菜单规格文本` + `菜单已启用 = 假`，返回"恢复浏览器默认菜单"）。若把清空 CEF 模型的行类型也叫 `clear`，**同一个词在同一工具里指两件完全不同的事**，必然误用。故行类型必须另起名。

- 施加：`清空菜单()`（`FBroLib.wsv:3313`）
- 回读验证：✅ `取数量()` == 0
- **硬守卫**（沿用既有禁令的思路，快照 9037 注释原文：「绝不能在规格为空时清空菜单: CEF 默认菜单会被清掉, 右键菜单直接消失」）：
  1. `wipe` 必须是规格**唯一一行**，否则拒绝（有其它行时清空语义无意义且危险）；
  2. 需调用方显式传 `confirm_wipe:true`，否则拒绝；
  3. 拒绝后必须给出可行动文案："清空后本次右键菜单将没有任何条目（用户会以为右键坏了）；且因每次右键都是全新默认模型，下一次右键会恢复 —— 若你要的是屏蔽右键，请用 browser_kernel_menu action=disable"。

**落点**：同 A3 两处。

## 4. 确实做不到 —— 逐条说明缺哪个接口 + 诚实降级

> 统一原则：**绝不编造标签、绝不静默返回空数组**。每一条都要求返回 `unsupported_reason`（点名缺失的类库接口 + `FBroLib.wsv` 行号）+ `unsupported_fields`。

### B1. 完整菜单快照（标签文字枚举）—— **做不到**
- 缺：`GetLabelAt(index)`（无）；现有唯一 getter `取菜单标签`（`FBroLib.wsv:3371`）**签名无参数**、语义不明（§1.7 三点证据）。
- 降级返回（放进 A1 的响应，**不要单独开工具**）：
  ```json
  { "labels": null,
    "labels_supported": false,
    "unsupported_reason": "类库未提供 GetLabelAt(index)；现有 取菜单标签(FBroLib.wsv:3371) 无入参、注释英文名误写为 GetMisspelledWord、原生调用只传模型(对比 置菜单标签 传 (模型,命令ID,标签), FBroLib.wsv:3382)，语义无法从源码确定，故不作为标签回读面。服务端不编造任何菜单文字。",
    "alternative": "① 用 action=list_command_ids 拿本服务自建项的标签(由规格文本自持, 是真实值不是猜的) ② 用 browser_event context_menu_opening 读上下文判断大概会显示哪些默认项 ③ 需要真实默认菜单文字请自行截图/OCR" }
  ```
  > 注意第 2 点的诚实性：**服务端自建项的标签是自己写的，属于"requested 值"而非"从菜单读回的值"**，必须放在 `requested_labels` 字段而不是 `labels`。

### B2. 按索引读命令ID —— **做不到**
- 缺：`GetCommandIdAt(index)`、`GetIndexOf(command_id)`。
- 降级：`{"command_id_at_index": null, "unsupported_reason": "缺 GetCommandIdAt/GetIndexOf，索引与命令ID 无法互映（FBroLib.wsv:3288-3624 无任何 At 后缀的命令ID 读写接口）"}`。
- **必须同时警告**：因此 `accel_by_index[i]` 与 `accel_by_command_id[id]` **是两套不可对齐的事实**，禁止服务端自行拼接成"条目 i 的命令ID 是 x"。

### B3. 按索引读条目类型 / 分组 / 可见 / 可用 / 勾选 / 子菜单 —— **做不到**
- 缺：`GetTypeAt` / `GetGroupIdAt` / `IsVisibleAt` / `IsEnabledAt` / `IsCheckedAt` / `IsSubMenuAt` / `GetSubMenuAt`。
- 降级：这些字段一律 `null` + `unsupported_reason` 逐项点名；**不要**用"名称含分隔栏就跳一个索引"之类的启发式去猜类型（CEF 分隔栏也会占索引，但偏移规律不可静态断言）。

### B4. 程序化弹出右键菜单 —— **做不到**
- 缺：类库**完全没有** `ShowMenu` / `ShowContextMenu` / `ShowPopupMenu` 之类接口。对 `FBroLib.wsv` 全文 grep `菜单` 的命中已全部列在 §1（36+21+2 个类声明与字段），无任何"显示菜单"方法。
- 降级：**不提供该工具**。若调用方要"弹出菜单"，返回失败 + 可行动替代：
  - "本服务无法用类库 API 弹出菜单。可发一次右键：`browser_mouse_click {button:\"right\"}`（走 CDP，不破坏会话）或 A1 的 `trigger=cef`（走 CEF 事件）。"

### B5. 程序化关闭已打开的菜单 —— **做不到**
- 缺：类库无 `CloseMenu` / `CancelMenu`；唯一"取消"入口是回调侧的 `类_FBrowser_运行命令菜单回调.取消()`（`FBroCallback.wsv:289`）与 `类_FBrowser_快捷菜单回调.取消()`（`FBroCallback.wsv:1032`），**都只在对应回调内有效**。
- 降级：不提供"关闭菜单"工具；只提供 A1 的 `context_menu_dismissed` 事件观察（已有，`MCP_BrowserEvents.wsv:2898`）。
- ⚠ 若真要做"收到菜单就自动取消"，只能在 `浏览器_菜单被调用`（2862）里用 `运行命令菜单回调.取消()` —— 但**推断**默认右键走 `OnBeforeContextMenu` 而非 `RunContextMenu`（CEF 语义：`RunContextMenu` 用于应用自绘菜单），所以这条路径**在默认菜单下大概率永不触发**。故必须先把 `context_menu_run` 事件的实际到达率摸清（观察，不是猜测），否则做出来的是"永不生效的假功能"。

### B6. 程序化"选定某个菜单项" —— 同上受限
- 可用接口：`类_FBrowser_运行命令菜单回调.继续(命令ID, 事件标识)`（`FBroCallback.wsv:281`）。
- 但目前唯一有实测价值的替代路径是**模拟点击**：`浏览器_菜单被点击` 事件已能观测到 `command_id`（`MCP_BrowserEvents.wsv:2888`），要"执行某命令"更可靠的做法是**直接调等价的编辑/导航工具**（`browser_edit_copy` / `browser_back` / `browser_reload` … 均已存在），而不是驱动菜单回调。→ **建议不做**任何基于 `继续()` 的工具。

### B7. 快捷菜单（QuickMenu）触发与控制 —— **做不到**
- 类库自证：`FBroEventControl.wsv:1153 / 1169 / 1183` 三处注释逐字写着"**待验证，未知触发条件**"。
- 现状：项目只 override 了其中 2 个并落库事件（`MCP_BrowserEvents.wsv:2908 / 2926`），**从未观测到**（我没有运行时访问权，不能断言"观测不到"；只能说：项目源码与工具描述里没有任何 quick_menu 已被触发的记录）。
- 降级：不提供任何 quick menu 工具。若要暴露只读查询，返回值必须带：
  ```json
  {"events": [], "supported": false,
   "unsupported_reason": "类库原文标注 '待验证，未知触发条件'(FBroEventControl.wsv:1153/1169/1183)，本服务无任何该族事件的到达记录，无法确认触发方式；空数组表示'未观测到'而非'不存在'"}
  ```

### B8. 颜色"是否被自定义过" —— **做不到**
- 现状：`取颜色_索引(i, 颜色类型)` 返回 `逻辑型` + 4 个出参（`FBroLib.wsv:3586`），类库**没有任何**"该颜色是否被显式设置过"的查询。
- 降级：每项报 `{"raw_return": true|false, "a":…, "r":…, "g":…, "b":…, "is_custom": null}`，并附
  `"unsupported_reason": "类库无'是否自定义颜色'查询；raw_return 的语义未确定(推断为 CEF GetColorAt 的成功与否)，is_custom 恒 null，禁止据此推断'用户改过颜色'"`。
- 另外 `颜色类型.计数 = 6`（`FBroConst.wsv:573`）不是真实颜色类型，遍历时**必须排除**，否则会多出垃圾字段。

### B9. 字体回读 —— **做不到**
- 类库只有 `置字体`(3609) / `置字体_索引`(3616)，**无 getter**；且两者自带 `注释 = "待验证"`。
- 降级：若开放（建议默认不开放），只报 `{"requested_font_list": "…", "verified": false, "unsupported_reason": "类库无字体回读接口（FBroLib.wsv:3609/3616 仅有 setter），且类库自带注释'待验证'；本服务只报请求值，不声称生效"}`。

### B10. 索引与命令ID 的映射 —— **做不到**（B2 的强化版，单列因为它会诱发错误推理）
- 缺：`GetIndexOf`。
- 降级：在 A1 响应里**新增一个显式字段** `index_to_command_id_supported: false`，并在 `unsupported_reason` 里点明："`accel_by_index` 与 `accel_by_command_id` **不可拼接**。"

### B11. 菜单项计数之外的"规模信息" —— 部分做不到
- 可读：`取数量()` = 条目总数（含分隔栏）。
- 不可读：**分隔栏个数**、**子菜单个数**、**层级深度**、**每层数量**（因为无 `GetTypeAt` / `IsSubMenuAt` / `GetSubMenuAt(index)`）。
- 降级：只报 `count`，并对上述字段明确 `unsupported_reason`；**不要**用"我自建的规格里有 N 个 sep"当成"菜单里有 N 个分隔栏"（那只是 requested 值，放入 `requested_composition` 字段）。

### B12. 修改浏览器**默认**菜单项 —— 项目已记录的既有限制（照抄，供交叉核对）
项目源码两处记录（快照 `MCP_Server.wsv:8915-8918` 与 8774 附近；工具描述 `MCP_Server.wsv:11031`）：

```
                    // 实测结论: 修改类只对**本服务自建项**(26500..28500)有效; 浏览器默认菜单项(100..130)
                    // 上 relabel/vis/dis/del 一律返回假、加删快捷键也不生效 —— 施加失败会由 apply_failed 报出。
```
```
            返回 ("[" + 类型名 + " " + 到文本 (命令ID) + " 未生效: 该ID是浏览器默认菜单项, 实测本应用不支持修改默认项] ")
```

### B13. 菜单项数量在**未设规格**时的读取 —— 当前**做不到**，但**可做**（不算硬阻塞）
见 §2.4 缺口 B。这不是类库缺失，是**本服务实现路径**造成的洞，由 §3-A1 补掉。此处单列以免与 B1-B11 的"类库硬阻塞"混淆。

## 6. 稳定性 / 崩溃风险，与"默认不暴露"建议

| 风险点 | 依据 | 建议 |
|---|---|---|
| **R1 `浏览器_菜单被调用`（RunContextMenu）是模态阻塞点** | 事件签名携带 `类_FBrowser_运行命令菜单回调`（`FBroEventControl.wsv:1114`），CEF 语义上应用需在**回调返回前**调用 `继续/取消`，否则菜单悬挂 | **默认不暴露**任何基于 `运行命令菜单回调` 的工具。现有实现恒 `返回 (假)`（`MCP_BrowserEvents.wsv:2874`）＝交给浏览器默认行为，是正确做法，**不要改** |
| **R2 菜单模型生命周期** | CEF 禁止回调外持引用；项目已记录（`MCP_BrowserEvents.wsv:2854-2855`） | A1 探针**只取值成文本**，绝不保存 `类_FBrowser_菜单模式` 对象到静态变量。这条是硬约束，违反即崩溃 |

## 9. 结论摘要（供主代理直接引用）

**菜单相关类库方法总数 = 63**

- `菜单模式` **18 / 36**（`MCP_Server.wsv` 的 `应用菜单规格`）
- `菜单环境` **18 / 21**（`MCP_Server.wsv` 的 `构建菜单环境摘要`）
- 两个回调类 **0 / 6**
- 7 个事件中 **6 个已 override 并落库**（`MCP_BrowserEvents.wsv`），1 个（`浏览器_即将运行快捷菜单`）**未 override**

**可实现（能回读验证）= 14 项**
菜单项数量(取数量) · 按索引读快捷键(存在/取快捷键_索引) · 按索引读颜色(取颜色_索引) · 按命令ID 读快捷键(存在/取快捷键) · 按命令ID 读颜色(取颜色) · 按命令ID 读类型/分组/可见/可用/勾选(取菜单类型/取分组ID/是否可见/是否禁止/是否选中) · 别名↔命令ID 双向解析 · 按索引设/摘快捷键(设置/移除快捷键_索引)+回读 · 按索引置颜色(置颜色_索引)+回读 · 按索引置勾选(选中状态_索引，无 getter 只能报 requested) · 清空菜单(清空菜单)+回读(高危，需三道守卫) · 菜单环境补 `取字典建议` · 菜单点击命令ID 观测(已有，缺文档) · 菜单关闭观测(已有)。
