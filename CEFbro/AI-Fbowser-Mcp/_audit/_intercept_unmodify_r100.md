## 4. 回答"能否按单条 URL 精确撤销"

### 4.1 类库能力判定

**能。** 两条通道各自具备"按地址取消单条"的能力：

| 通道 | 添加 | 取消单条 | 键 |
|---|---|---|---|
| VIP 过滤器 | `过滤器_修改内容` / `过滤器_替换资源_数据` / `过滤器_替换资源_文件`（`FBroVip.wsv:1134/1162/1174`） | `过滤器_取消修改内容` / `过滤器_取消替换资源`（`FBroVip.wsv:1147/1186`） | `目标地址`（文本，注释要求"完整地址"、"和之前设置的目标地址一一对应"） |
| 手写 ResponseFilter | `添加资源替换规则`（`MCP_Server.wsv:7145`） | **无现成方法** —— 必须新增"按 URL 删行" | 规则行第 2 段（经 `规则字段转义` 的 URL），匹配口径是**子串** |

**是"按 URL 取消"，不是"按索引取消"**：两组取消 API 都**只有一个 `目标地址` 文本参数**，没有任何索引/句柄参数。`[原文]` 证据：`FBroVip.wsv:1147-1148`、`1186-1187`、`126-127`、`161-162`。

### 4.2 同一 URL 被 `modify` 两次时的行为

- **手写通道**：`[原文]` 添加时**不去重**（`7145-7176` 只做追加 + 裁剪）；匹配时**第一条命中即跳出**（`7257 跳出循环`）。故 `[推断]`：**第一次（最旧）的规则生效，后来的同 URL 规则是死规则**（仅当旧规则因超过 500 条上限被 `裁剪规则文本到最大行数` 淘汰后才可能轮到最后一条）。因此"按 URL 撤销"若删掉**所有**同 URL 行，会把那条**正在生效**的旧规则一起删掉 —— 语义上是对的（用户要的就是"这个 URL 别再改了"），但返回信息必须说清删了几条，否则用户以为只删了一条。
- **VIP 通道**：`[原文]` 类库注释明说 `过滤器_修改内容` 可对同一目标多次调用（`FBroVip.wsv:1136`："如果同一个目标存在多个需要修改的数据，多次调用本方法即可，**但要注意目标地址和匹配模式要保持一致，否则可能会出错**"）。取消 API 只接受地址、不接受模式 → **同地址多模式注册后单地址取消的实际行为：[判不出]**（底层 `FBroHsVIPControl_DeletResponseFiltereChangeData` 的 C++ 实现不在只读资料内）。同理，"取消一个不存在的地址是否有副作用" **[判不出]**（类库方法返回 void，无返回值，`FBroVip.wsv:1150-1151`）。

### 4.3 `unmodify` / `unreplace` 的精确实现落点

#### 落点 A：新增手写通道"按 URL 删行"辅助方法（`MCP_Server.wsv`）

**插入位置：`MCP_Server.wsv:7176` 之后**（即 `添加资源替换规则` 的闭合 `}` 之后），与 `匹配资源篡改规则`（`7180`）之间。同区段内便于和 `规则字段转义/反转义`（`7119/7133`）复用。

建议新增一个（或两个）静态方法，必须复刻既有约定：

1. **签名形状**（与邻居一致，带 `@输出名` / `@强制输出`）：
   - 参考 `7145`：`方法 添加资源替换规则 <公开 静态 @输出名 = "AddResourceReplaceRule" @强制输出 = 真>`
   - 建议：`方法 移除资源替换规则 <公开 静态 类型 = 整数 @输出名 = "RemoveResourceReplaceRule" @强制输出 = 真>`
   - 参数：`规则URL <类型 = 文本型>`、`动作过滤 <类型 = 文本型>`（空=不限动作）、可选 `同时清文件缓存 <类型 = 逻辑型>`；返回"实际删除行数"。
2. **必须持锁**：整段包在 `规则锁.加锁 ()` / `规则锁.解锁 ()` 之间（照抄 `7165/7175`），否则与 CEF 线程读（`MCP_BrowserEvents.wsv:392/406`）撕裂。
3. **必须对入参做 `规则字段转义`** 后再与第 2 段比较 —— 因为落盘时 URL 是 `规则字段转义 (规则URL)`（`7155`）。
4. **拆行/重组**：`分割文本 (资源替换规则, "\n", 行数组, 真, 假)`（照抄 `7193`），逐行 `分割文本 (行文本, "|", 段数组, 假, 假)`（照抄 `7204`），按 `段数组.取成员 (1)` 的**反转义值**与目标 URL 做**同一口径**比较。**口径建议**：默认用"相等"（因为入参 url 本来就是用户原样给的键），若要与命中语义一致则用 `寻找文本 (行URL, 目标URL, 0, 假) != -1`（子串，照抄 `7214`）—— 二者必选其一并**在返回文本里写明口径**。
5. **重组后必须再过 `裁剪规则文本到最大行数`**（`7046`），否则删行不会触发上限回收（其实删行只会变短，但保持一致更安全）。
6. **返回实际删除条数**，供 action 层如实回话。
7. **同步清 `篡改文件缓存*` 数组**：若被删行是 `replace_file`（行内含 `file:` 段，格式见 `7161-7164`），应把对应路径从 `篡改文件缓存路径/篡改文件缓存内容` 两个**平行数组**里成对删除（删法照抄 `7458-7459`），否则出现"规则已撤但文件内容还缓存着"的幽灵（虽然不再被引用，但会一直占内存，且 `clear` 也不清它）。

#### 落点 B：新增 action 分派分支（`MCP_Server_Core.wsv`）

**精确插入位置：`MCP_Server_Core.wsv:2609` 的 `}` 之后、`2610` 的兜底 `返回 (...)` 之前。**

因为 `2540 如果 (action == "modify")` 开启的是一条 `否则链`（`2555/2564/2587/2593` 依次 `否则`），把新分支写成 `否则 (action == "unmodify")` 追加在 `2609` 之后，正好接到链尾，且**自动继承 `2504-2509` 的 `url` 必填校验**。原文锚点：


**若还要支持"撤销导航规则"（`navigate_unblock` / `navigate_unredirect`）**：`2511` 不是链的一部分，所以新分支要么也写成**独立 `如果`**（照抄 `2511` 的缩进与形态，可放在 `2538` 之后），要么把新分支同样追加在 `2609` 之后作为 `否则`（此时它接在 `2540` 链上，行为等价，因为 `url` 已在 `2504` 取到）。**注意导航规则行不做转义**（`2519` 直接拼 `url`），删行比较时用**原文**而非转义值 —— 这是与资源通道的**关键差异**，写错就永远删不掉。

## 5. 风险与边界

### 5.1 URL 匹配口径是否与添加时一致

| 环节 | 口径 | 原文锚点 |
|---|---|---|
| 手写通道：添加时写入 | URL 原样（仅转义 `% \| \n \r`），**不校验**、不规范化 | `MCP_Server.wsv:7155` + `7119-7129` |
| 手写通道：请求命中 | **子串 + 不区分大小写**（`寻找文本(目标URL, 规则URL, 0, 假)`） | `MCP_Server.wsv:7214` |
| 手写通道：导航命中 | **子串 + 不区分大小写** | `MCP_BrowserEvents.wsv:1221` |
| 导航规则：添加时写入 | 原样拼接，**不转义** | `MCP_Server_Core.wsv:2519` |
| VIP 通道 | 由 `匹配模式` 决定（默认 `完全匹配` = 完整地址相等）；注释警告同目标多次调用需"目标地址和匹配模式保持一致" | `FBroVip.wsv:1137/1138/1136`；`FBroConst.wsv:602` |

**结论**：**不一致**。添加时"存原样"，命中时"子串、忽略大小写"。因此撤销的匹配口径必须**显式选择并写明**：

- 选"**相等**"（推荐做默认）：语义精确，`unmodify(url="a.js")` 不会误删 URL 为 `https://x/a.js` 的规则（因为存的是 `a.js` 时它们本来就相等）。风险是用户按"命中口径"的心智去撤销会删不到 → 返回 `removed:0` 时必须提示"请传与添加时完全一致的 url 串"。
- 选"**子串**"（与命中口径对齐）：符合"所见即所撤"，但会**一条命令删多条**（例如 `unmodify(url=".js")` 会删掉所有 `.js` 规则）→ 必须把 `removed` 数量如实回给调用方。

额外边界：手写通道 `url` 中若含 `|` 或换行，落盘时被转义（`7124-7127`），**撤销比较必须用转义后的串**；导航通道不转义（`2519`），比较用原文 —— 两条通道规则相反，最容易写错的地方。

### 5.2 撤销不存在的规则：成功还是失败？

**建议：幂等成功 + 如实说明。** 理由：

1. 与本项目既有惯例一致：`clear` 无论有无规则都返回 `命令成功`（`MCP_Server_Core.wsv:2449`），`popup_disable` 也无条件成功（`2501`）。
2. MCP 的调用方是 AI/Agent，常见行为是"重试直到成功"。返回失败会诱发重试风暴，而重试永远不会成功（规则本来就不存在）——这是典型的**不可恢复的假失败**。
3. 撤销的**目标状态**是"该 URL 不再被改"，不存在时该目标**已经达成**，成功语义正确。
4. 但必须**如实说明**：返回文本应形如 `"未找到匹配规则(url=...), 状态未变更 (removed=0) | 口径: url 完全相等(区分/不区分大小写) | 当前资源规则 N 条"`，否则调用方无法区分"撤销成功"与"我 url 写错了导致什么都没撤"。这一点是本项目 `2610`/`3539` 已有的"如实说明"风格（见 `3539` 那段"⚠ 实测说明"）。

**唯一建议返回失败的场景**：无法判定时的**结构性错误**（None），即 `资源替换规则` 文本被外部破坏、或锁竞争导致读不到（`[推断]`：现有代码没有超时/失败路径，`规则锁.加锁()` 无返回值，所以这条实际不可达）。

### 5.3 是否需要同时处理"手写通道"和"VIP 过滤器"两套状态

**需要，但要分清"现在"和"将来"：**

- **现在（本工作树）**：`browser_intercept` 的全部规则动作走手写通道（`2540-2609` 全部调用 `添加资源替换规则`）。VIP 通道**只有关闭时的 `全部取消`**（`8557/8558`）。所以新增 `unmodify/unreplace` **只需处理手写通道**即可做到"不产生幽灵"。
- **但必须如实告知用户**：`clear` 的返回文本自称"手写过滤器通道"（`2449`），且**不清 VIP 状态**；同理新的 `unmodify/unreplace` 也**只清手写通道**。若将来有人用 `browser_vip_*` 或直接 `过滤器_修改内容` 加了 VIP 规则（类库能力存在，且 `解析匹配模式` 这个死代码 + 备份里的 `match_mode` 属性说明原设计有此意图），则撤销必须**同时**调用 `过滤器_取消修改内容(完整地址)` / `过滤器_取消替换资源(完整地址)`。
- **实现建议**：在返回文本里固定带一句"作用域: 手写过滤器通道(不含 VIP 过滤器)"，把"两套状态"这件事**显式暴露**，而不是静默遗漏。这也和 `3539` 那种"把已知限制写进返回文本"的既有风格一致。
- **VIP 族选择**：若将来接线，必须与添加同族 —— 要么全用 `类_FBrowserVIP_控制器`（`FBroVip.wsv:1134-1199`），要么全用 `FBrowserVIP全局功能`（`FBroVip.wsv:114-172`）。`MCP_Server.wsv:8557` 用的是**控制器族**。

### 5.4 其它风险与边界（`[原文]` 支撑）

1. **刷新才生效**：既有所有规则类成功文本都带"刷新页面后生效"（`2551/2562/2583/2591/2608`）。手写通道没有类似 VIP 例子的 `重新载入_忽略缓存`（`main14.wsv:706/731`）调用。→ 撤销后的提示文本也应保留"刷新页面后生效"，并可考虑提示浏览器缓存。
2. **飞行中响应不受影响**：`MCP_BrowserEvents.wsv:406` 是在**每次请求时**读规则，因此删行只影响**后续**请求；已在传的响应体继续按旧规则改写。`[推断]`。
3. **500 条上限与静默淘汰**：`MCP_Constants.wsv:40` = 500。`裁剪规则文本到最大行数`（`7046`）在超限时**淘汰最旧并打日志**（`7063`）。→ 若用户"撤销不存在"，可能真实原因是那条规则**已经被上限淘汰**了。返回文本可提示当前规则条数，便于自查。
4. **规则顺序即优先级**：`7257 跳出循环` 意味着"先加者优先"。**撤销后不应做任何重排**（例如把删掉的行再补回去），否则会改变已生效的规则优先级。
5. **`replace_file` 的 `file:` 段位置不对称**：写入在**文件路径段**（`7163`，紧跟替换文本段后），读取却从**搜索段**取 `file:` 前缀（`7244-7248`），并限定 `规则动作 == "replace_file"`。撤销删行时若要把 URL 从文件缓存数组里摘掉，需按**实际行格式**解析，不要照抄读取端的逻辑。
6. **并发**：CEF 回调线程读（`MCP_BrowserEvents.wsv:392-406`）与 MCP 线程写必须靠 `规则锁`（`362`）互斥；新辅助方法**漏锁会造成撕裂读**（既有注释 `7105-7106` 专门为此加了 `取导航规则快照`）。
7. **导航规则撤销的独立坑**：`2519 新行 = 规则动作 + "|" + url` 未转义，url 含 `|` 时导航规则本身就已经"加错了"，撤销也无从谈起 —— 属于既有缺陷，非本次引入。
