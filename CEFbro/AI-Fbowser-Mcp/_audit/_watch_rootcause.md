## 0. 一句话根因（供快速传达）

> **变更的"写入段"和"事件日志读出段"都在，但 `list` 分支从头到尾没有读事件日志的代码；而且即使补上读取，写入侧与读出侧的键名/浏览器 ID 也双双对不上** ——
> 写入：`记录事件日志 ("watch_changed", 键, 0, ...)`（`log_type = "watch_changed"`，`event_name = <watch键>`，`browser_id = 0`）
> 读出：`查询事件日志 ("browser_event" | "app_event", <事件名>, <主浏览器ID>, ...)` 与 `查询事件日志 ("", "", <主浏览器ID>, ...)`
> 两边 `log_type` 不同、`browser_id` 一侧恒为 0 一侧恒 >0，**任何一条 `watch_changed` 行都不可能被现有读者命中**；`list` 更是只返回任务定义、不返回变更。

> **结论（高置信度）**：这条链上"空响应"= **HTTP 200 且 body 长度 0**（或 stdio 一个字节都不写）⇔ **`处理MCP请求` 返回了 `""`**。项目自己的桥接脚本给这个现象的名字就是 **"MCP 服务器返回空响应"**。因此"整个响应变空"不是"JSON 拼坏了"，也不是"字段为空"，而是**请求处理函数返回空串**。

### 2.1 假说 H-A（置信度：中高 ≈ 60%）：其实不是"整个响应空"，而是**新加的 `changes_json` 本身就是 `[]`**

- 机制：加了 `changes_json` 但读出的恒为 `[]`。依据 §1.4(c) 的两道过滤：`log_type='browser_event'`（或 `''`）、`browser_id=<主浏览器ID>`；而写入行是 `log_type='watch_changed'`、`browser_id=0`。**两条路都不匹配 → `查询事件日志` 永远返回 `"[]"`**。
- 支持证据：`MCP_Kernel.wsv:1000` 的注释原文写的是"list 返回**空响应**"，而不是"报错 / 超时 / 结果解析失败"；对一个新增字段而言，"字段值为 `[]`"被口头描述成"空响应"是很自然的。并且回退注释把归因写成"该上下文不能调用 `查询事件日志`（疑与其内部锁/线程上下文有关）"，这个归因**与 §1.4 的硬证据相矛盾**——同一上下文里 `分派_CDP监控` 的 `list` 分支**正在**调用它，且该工具已被项目自己标记为"✅ 端到端可用"：

```
        st.加入文本成员 ("events_json", MCP命令服务器.查询事件日志 ("cdp_monitor", "", 0, 200))
        返回 (MCP_响应构建.命令成功_原始JSON (命令ID, st.到可读文本 (YYJSON格式化选项.压缩)))
```
（`src\MCP_Kernel.wsv:696-697`）

- ★ 判定方法：复现时看响应体是否 **200 且有 body**，且 body 内 `changes_json` 为 `"[]"`。若是，则 H-A 成立，且**回退所依据的结论是误判**（正确方向被错误回滚）。

### 2.2 假说 H-B（置信度：中 ≈ 30%）：响应体**真的**为空，因为请求线程在 `查询事件日志` 内异常终止

- 机制：`处理MCP请求` 返回 `""` → HTTP 发 `200 + 长度 0`（`MCP_Server_HTTP.wsv:110`）。
- 能返回 `""` 的代码路径（穷举 `tools/call` 路径）：
  1. **被判为通知**：`是通知 = 请求ID == ""`（`MCP_Server.wsv:8994-8995`），而 `tools/call` 分支先执行工具、再丢弃响应：
     ```
             工具响应文本 = 处理_工具调用 (请求ID, 解析结果)
             如果 (是通知)
             {
                 返回 ("")
             }
     ```
     （`MCP_Server.wsv:9135-9139`）——**"命令真的执行了、值真的变了，但响应被丢成空"**，与用户描述的"值确实变了却报不出来"字面吻合。但 `请求ID` 的提取已对数值 id 做了兜底（`MCP_Server.wsv:8896-8910`），所以这条更可能是**次要**因素。
  2. **请求线程在读取内崩掉**：`查询事件日志` **独缺** `缓存数据库可用 ()` 守卫，而项目里其它同类函数都有：

     | 函数 | 是否有"数据库可用"守卫 |
     |---|---|
     | `记录事件日志`（写） | ✅ `MCP_Server.wsv:4713-4716` `如果 (缓存数据库可用 () == 假) { 返回 }` |
     | `存储任务结果`（写） | ✅ `MCP_Server.wsv:4623-4626` 同上 |
     | `查询事件日志`（读） | ❌ **无任何守卫**，`MCP_Server.wsv:4776` 直接 `异步缓存锁.加锁 ()` → `4805` `记录集 = 缓存数据库.取记录集 (sql, )` |

     在 `缓存数据库已打开 == 假`（DB 打不开时降级/`MCP正在关闭`/关闭窗口，见 `MCP_Server.wsv:4248` `缓存数据库已打开 = 真` 与 `4257` `缓存数据库已打开 = 假`）时，对未打开的 SQLite 句柄建语句/绑参数属**运行期**故障面，可能让请求线程在发出响应前终止 → 客户端只看到空 body。注释里"编译与快检均正常，属**运行期**问题"这一措辞与该形态一致。
- ★ 判定方法：复现时抓原始 HTTP：**200 且 `Content-Length: 0`** → H-B 成立（且说明是"空 body"，而非"字段为空"）；同时看服务端控制台在 `[MCP] 执行:browser_kernel_watch` 之后是否还有 `[MCP] RPC方法:` / 响应完成日志。

### 2.3 假说 H-C（置信度：中低 ≈ 15%）：外层 JSON 不合法 → 但**应当**返回可见错误，与"空响应"不符

若把 `changes_json` 用字符串拼接挂到 `构建简单JSON` 的产物后面（例如 `返回 (构建简单JSON (...) + 变更JSON)`），会得到 `{"success":true,...}[...]` 这种**非法 JSON**；此时 `MCP_Server.wsv:10074-10078` 会拦截：

```
        变量 结果解析 <类型 = YYJSON只读对象类>
        如果 (结果解析.创建自文本 (命令结果JSON) == 假)
        {
            返回 (构建JSONRPC响应 (请求ID, "", -32603, "结果解析失败: " + 工具名))
        }
```

→ 客户端应看到 **`-32603 结果解析失败: browser_kernel_watch`**（可见错误文本，HTTP body 非空）。**除非**客户端把 JSON-RPC `error` 渲染成空白，否则这条**与"空响应"不符**，故列作排除性假说。
另注：`构建简单JSON` 只支持**单键**，且只有 `network_logs` / `console_logs` 两个键名走"原样嵌入 JSON"的快速分支（`MCP_ResponseBuilders.wsv:265`），其余键名一律走 `加入文本成员`（数组会被转义成字符串）。若新增字段用了别的键名而期望它是 JSON 数组，会得到**被转义的字符串**（形状错但不为空）。

### 2.4 假说 H-D（置信度：低）：死锁/长阻塞 → 客户端超时（不是 200 空体）

- 已做的排除性核查：
  - 派发路径只持 `MCP执行锁`，**没有**持 `异步缓存锁`：`MCP_Server.wsv:10311` `MCP执行锁.加锁 ()`，`10393` `MCP执行锁.解锁 ()`（其间无 `异步缓存锁`）。
  - 锁序有明文约定且无反序：`MCP_Server.wsv:8658` `// 锁顺序: 协议锁 → MCP执行锁 → 异步缓存锁 (全项目无反向获取)`。
  - `互斥锁类` **可重入**（`审计报告-火山语法与逻辑.md:517`："`batch` 嵌套调用是否自锁 | **不死锁**。`互斥锁类` 可重入"）。
  - UI 线程（`main.wsv:125/160`）不会调用 `执行浏览器命令`/`处理MCP请求`（调用点全部在请求路径：`MCP_Server.wsv` 内 4 处 —— 含 `10066` 与 `执行浏览器命令` 定义 `10306` 附近、`MCP_Server_Workflow.wsv:586`、`MCP_Server_Core.wsv` 内 1 处），因此不存在"UI 持 DB 锁 → 要协议锁"的 ABBA 环。
  - 残留非零风险：UI 线程每 500ms 可能经 `检查定时监视 → 记录事件日志` 持 `异步缓存锁` 做 SQLite INSERT；MCP 线程此时在 `查询事件日志` 里等这把锁 → **会让请求多等一段 INSERT 时间**（毫秒级，正常不成灾），但极端情况下（DB 文件锁/磁盘慢）会表现为"变慢"甚至客户端超时，而**超时不是"空响应"**。
- ★ 判定方法：客户端报的是"超时"还是"空 body"。

### 2.5 交叉证据：同类"只写不读"缺陷在本项目已复现两次，且**判据修好了也没用**

项目自己的报告已记录：`cdp_monitor` 与 `watch_changed` 属同一模式（"写入 event_log 的 log_type 全项目无读取方"）；`cdp_monitor` 是靠**在 `list` 里现加读取**才修好的（`MCP_Kernel.wsv:693-697` 的注释原文）：

而 `watch` 的采样判据（`MCP_Kernel.wsv:1089`）已按同一范式修好、副作用探针也证实"确实在跑"，**唯独读取段与键名对齐这两件事没做** → 与本报告 §0 的结论一致。

#### 乙-5 新增助手 `取监视变更JSON`（把平行数组拼成合法 JSON 数组文本）

放在 `取监视平行值`/`置监视平行值` 之后（即 `1161` 的 `}` 之后、`1163` 的 `# ==================== 全事件流一键开关 ====================` 之前）。
**注意**：值本身就是 JSON 文本，必须以**原文嵌入**方式拼（不能转义），键名要转义；写法照 `MCP_Kernel.wsv:676-691` 的 `模式列表` 范式 + `MCP_响应构建.JSON转义文本`：

```
    方法 取监视变更JSON <公开 静态 类型 = 文本型 @输出名 = "GetWatchChangesJSON" @强制输出 = 真>
    {
        变量 结果 <类型 = 文本型>
        结果 = "["
        变量 首项 <类型 = 逻辑型 值 = 真>
        计次循环 (监视变更记录.取成员数 ())
        {
            变量 条目 <类型 = 文本型>
            条目 = 监视变更记录.取成员 (取循环索引 ())
            变量 等号位 <类型 = 整数>
            等号位 = 寻找文本 (条目, "=", 0, 假)
            如果 (等号位 > 0)
            {
                如果 (首项)
                {
                    首项 = 假
                }
                否则
                {
                    结果 = 结果 + ","
                }
                变量 变更键 <类型 = 文本型>
                变更键 = 取文本左边 (条目, 等号位)
                变量 变更值 <类型 = 文本型>
                变更值 = 取文本右边 (条目, 取文本长度 (条目) - 等号位 - 1)
                结果 = 结果 + "{\"watch_key\":\"" + MCP_响应构建.JSON转义文本 (变更键) + "\",\"count\":\"" + MCP_响应构建.JSON转义文本 (取监视平行值 (监视变更计数, 变更键)) + "\",\"last\":" + 变更值 + "}"
            }
        }
        结果 = 结果 + "]"

    }
```

**说明**：`变更值` 是 `变更数据.到可读文本 (...)` 的产物（合法 JSON 对象），故原文嵌入不会产生非法 JSON；`watch_key`/`count` 是要嵌入字符串的，必须转义（`JSON转义文本` 存在，见 `MCP_ResponseBuilders.wsv:212`）。

**风险（路径乙）**：
1. **只有"最近一次"**：覆盖写会丢历史（每次变更的时间序列）。需要历史就必须改成追加式数组或保留 N 条环形缓冲 —— 那会引入"什么时候裁剪"的新问题（本项目已有 `事件日志最大条目`/`缓存清理_保留缓冲` 这类常量可参照）。
2. **内存态、重启即失**（事件日志是落 SQLite 的，两者持久性不同）。
3. **不加锁**：`监视变更记录` 会被 **UI 线程**（`检查定时监视`，每 500ms）写、被 **MCP 线程**（`list`）读；现有 4 个平行数组同样无锁（`886-889`），属既有设计，但新增共享可变状态会**放大**该风险（`监视任务.删除成员` 与 `计程循环 取成员数()` 的组合本就存在"取数后数组变短→越界"的窗口，`957-971` vs `1022-1025`）。若要稳妥，应给这 6 个数组加同一把 `MCP执行锁` 之外的小锁，或把写入改为"先拷快照"。
4. **`browser_event` 时间线仍然看不到 `watch_changed`**（路径乙不写日志即不解决"时间线"口径；写了日志但读不出则仍是 H-A）。所以**乙不能替代甲**，两者互补。
5. 改 `list` 返回结构相当于**改这个工具的对外契约**（`watches` 从"字符串化的数组"变成同名字符串、新增 `changes_json`，且外层改为带 `id`/`success` 的 `命令成功_原始JSON`）→ 依赖旧响应的调用方（若有）需要同步。

## 4. "重复追加（`yyjson_mut_obj_add_*` 同名键）"专项核查结论

**核查对象**：`browser_kernel_watch` 的写入路径是否存在与"11 处已改覆盖写"同类的重复键问题。

### 4.1 该坑的确切形态（逐字，`_audit\fix_dupekey.py:4-6`）

```
根因见 MCP_Server.wsv 中 覆盖整数成员/覆盖文本成员 的注释:
  加入X成员 = yyjson_mut_obj_add_* (追加, 不覆盖) ; 取X = yyjson_obj_get (返回第一个)
  => 对象里出现重复键, 读回旧值, 状态机永远推进不了。
```
实机证据注释在 `src\MCP_Server.wsv:6520-6526`，覆盖写实现见 `6528-6552`（`覆盖整数成员`/`覆盖文本成员`：先 `对象.删除成员 (键名)` 再 `加入X成员`）。

### 4.2 逐点核查结果：**未发现同类重复追加**

| 核查点 | 位置 | 结论 |
|---|---|---|
| 变更数据对象 `变更数据` | `MCP_Kernel.wsv:1058-1063` | ✅ 干净：每次 `创建自文本 ("{}")` **新建**，4 个键 `key`/`previous`/`current`/`time_ms` **互不相同**，无重复追加 |
| 任务对象 `新任务` / `新任务2` | `MCP_Kernel.wsv:927-944` | ✅ 干净：同样新建，3 个键互不相同；同 key 覆盖走的是 `数组置成员 (监视任务, 索引, 新JSON)`（**整项替换**，不是往同一对象里再追加） |
| 监视状态（上次值/提交态/提交毫秒） | `MCP_Kernel.wsv:1066/1069/1079/1091` | ✅ 不走 yyjson：`置监视平行值` → `数组置成员`（`1100-1119`）是**重建保序的原位覆盖**；`取监视平行值`（`1123-1140`）用 `键 + "="` 前缀匹配 + 长度切尾，**值里含 `=` 也不串位** |
| 键前缀误匹配 | `MCP_Kernel.wsv:1133/1150` | ✅ 无碰撞：`寻找文本 (条目, 键 + "=", 0, 假) == 0` 要求"键+等号"在起始处，`ab=1` 不会被键 `a` 命中的前提是 `键 + "="` 为 `a=`，而 `ab=1` 不以 `a=` 开头 |
| `list` 响应对象 | `MCP_Kernel.wsv:1003` | ⚠️ 当前用 `构建简单JSON`（单键、且该键名不在 `network_logs`/`console_logs` 快速分支内 `MCP_ResponseBuilders.wsv:265`）。**目前只有一个键，无所谓重复**；但**这正是"加 `changes_json` 时的坑位**"：若在同一个 `YYJSON对象类` 上二次 `加入文本成员 ("watches", ...)` 或对已存在的键再次 `加入`，就会进入"重复键读旧值"形态 |

### 4.3 结论与提醒

- **`browser_kernel_watch` 的写入路径（`event_log` 写入 + 4 个平行数组）不存在同类重复追加问题** —— `list` 为空的**真因不是**这个坑，而是 §0 的"读出段缺失 + 键名/browser_id 不匹配"。
- 但**同类坑在本工具的"修复动作"里极易被引入**：如果按路径乙/甲的思路，往一个**已存在同名键**的 `YYJSON对象类` 上再次 `加入文本成员`（例如先 `加入文本成员 ("changes_json", 旧值)` 再 `加入文本成员 ("changes_json", 新值)`，或对 `构建简单JSON` 的产物做二次对象化追加），就会复现"读回旧值"。**建议**：新增字段一律**只写一次**；若必须重复写同一键，用现成的 `MCP命令服务器.覆盖文本成员 (对象, 键, 值)`（`MCP_Server.wsv:6541`）。
