## 2. 【HIGH】缺陷

### 2.1 断点调试家族：5 个 `boolean` 参数的"非默认值"全部被静默忽略

**根因（作者已在别处记录并修复，但此处遗漏）** —— `MCP_Server.wsv:5802` 注释原文：

> `// 修复: 到文本()对布尔/数值节点返回空串, 原字符串归一化判别对非文本节点失效;`
> `// 改用 取类型() 按节点类型取值 (布尔/数值/文本分别处理, 缺失键类型=未知回默认)`

即 `yyjson取文本` 内部映射到 `yyjson_get_str`，**对 JSON 布尔节点返回空串 `""`**。因此"用 `取文本` 读布尔参数再与 `"true"/"false"/"1"/"0"` 比较"这一模式对**真布尔输入恒为空串**，比较永远为假，分支不可达。作者已把 `yyjson取逻辑_默认`（`MCP_Server.wsv:5797+`，改用 `取类型()`）改造正确，但下列 5 处仍是旧模式：

| # | 位置 | 键 | 受影响工具 | schema 默认值 | **被忽略的值** | 后果 |
|---|---|---|---|---|---|---|
| 1 | `MCP_Server_Core.wsv:4362` | `parse` | `browser_debugger_evaluate` | false | **`parse:true`** | 显式要求"同步解析结果"被忽略，永远走异步 `Debugger.evaluateOnCallFrame` 路径 |
| 2 | `MCP_Server_Core.wsv:4394` | `fresh` | `browser_debugger_wait_paused` | false | **`fresh:true`** | 不清除旧事件 → 可能立即返回**上一次遗留的 `Debugger.paused`**，断点流程误判"已暂停" |
| 3 | `MCP_Server.wsv:2522` | `expand` | `browser_debugger_evaluate` / `_flow` / `_inspect` | true | **`expand:false`** | 无法关闭 object/function 属性展开 |
| 4 | `MCP_Server.wsv:2534` | `return_by_value` | `browser_debugger_evaluate` / `_flow` / `_inspect` / `browser_reverse_runtime` | true | **`return_by_value:false`** | 无法关闭 returnByValue |
| 5 | `MCP_Server.wsv:2683` | `resume` | `browser_debugger_flow` | true | **`resume:false`** | **求值后仍会自动 resume** —— 用户想停在断点继续检查，工具却继续执行 |

**证据（代表性三处原文）**：

```火山
// MCP_Server.wsv:2518-2527
方法 取Debugger求值展开 <公开 静态 类型 = 逻辑型>
{
    变量 t <类型 = 文本型>
    t = yyjson取文本 (参数JSON, "expand")
    如果 (t == "false" || t == "0") { 返回 (假) }
    返回 (真)
}

// MCP_Server.wsv:2682-2690
resumeText = yyjson取文本 (参数JSON, "resume")
如果 (resumeText == "false" || resumeText == "0") { 返回 (假) }
如果 (resumeText == "true" || resumeText == "1") { 返回 (真) }

// MCP_Server_Core.wsv:4361-4363
parseText = MCP命令服务器.yyjson取文本 (参数JSON, "parse")
如果 (parseText == "true" || parseText == "1") { ... 同步解析分支 ... }
```

而 schema 确实声明为 `boolean`（`MCP_Server.wsv:8361` `属性项JSON ("parse", "boolean", ...)`、`:8362` `("fresh", "boolean", ...)`、`:8365` `("expand"…)`/`("return_by_value"…)`/`("resume"…)`）。规范客户端按 schema 发送 JSON 布尔 `true`/`false`，因此**每个参数的非默认值都读不到**。

**影响面**：断点调试是产品宣传的核心能力之一（"CDP Debugger 断点调试"），这 5 个参数正是控制调试行为的关键开关；`resume:false` 被忽略会导致"想停却继续跑"，`fresh:true` 被忽略会导致读到上一次的陈旧暂停事件 → **调试结论可能错误**。

**修复**：5 处统一改用已有的 `MCP命令服务器.yyjson取逻辑_默认 (参数JSON, "键名", 默认值)`（该函数已按节点类型正确取值）。这是一处**低风险、高收益**的收敛修复。

**扫描证据**：对 41 个 schema 声明为 `boolean` 的参数名 × 312 个 `yyjson取文本` 调用点做全项目交叉扫描，命中恰好 **5 处**（上表全部），无其它遗漏；另确认**不存在**"同一参数在 schema 中被声明为多种类型"的自相矛盾。

### 2.2 `browser_vip_set_is_trusted`：schema 广告 `enable`，实现读 `value` → 开关永远无法启用

| 项 | 内容 |
|---|---|
| schema | `MCP_Server.wsv:8471`：`添加工具JSON ("browser_vip_set_is_trusted", "VIP: 设置Event.isTrusted", 单参数Schema文本 ("enable", "boolean", "启用isTrusted"))` |
| 实现 | `MCP_Server_VIP.wsv:1434`：`vp.内核开关_设置EventIsTrusted (MCP命令服务器.yyjson取逻辑 (参数JSON, "value"))` |

客户端按 schema 传 `{"enable": true}`；实现却读 `"value"` —— 该键在 schema 中**从未被广告**，客户端不会传。`yyjson取逻辑` 对缺失键返回 `假` → **`isTrusted` 恒被设为 false，永远无法启用**，而工具照样返回"成功"。

这是"键名错位"型缺陷（与 2.1 的"类型错配"型并列），也是全项目唯一一处确认的键名错位 —— 其余工具的 schema 键名与实现读取键名**逐项一致**。

**修复**：`"value"` → `"enable"`，或把 schema 参数名改为 `value`（二选一，保持一致）。

### 2.3 `mcp://` 资源处理器 `读取` 丢弃 `取字节集右边` 返回值 → 大响应体在首块上无限循环

**位置**：`src/MCP_Kernel.wsv:1616-1636`（关键行 **1627**）

```火山
方法 读取 <公开 @虚拟方法 = 可覆盖>          // 类_MCP_方案资源处理器
参数 标识ID <类型 = 长整数>
参数 输出数据指针 <类型 = 变整数>
参数 读取大小 <类型 = 整数>
参数 读入大小 <类型 = 整数类>
参数 资源读取回调 <类型 = 类_FBrowser_资源读取回调>
{
    变量 size <类型 = 整数>
    size = 响应字节集.取字节集长度 ()
    如果 (size == 0) { 返回 (假) }
    如果 (size > 读取大小)
    {
        内存复制 (输出数据指针, 响应字节集.取字节集指针 (), 读取大小)
        读入大小.值 = 读取大小
        取字节集右边 (响应字节集, size - 读取大小)      // ← 返回值被丢弃！缓冲区未缩短
    }
    否则
    {
        内存复制 (输出数据指针, 响应字节集.取字节集指针 (), size)
        读入大小.值 = size
        响应字节集.清空字节集 ()                        // ← 对照：这里才是正确的消费
    }
    返回 (真)
}
```

**`取字节集右边` 的真实语义（已核实到类库源码）** —— `资料/类库/视窗基本类/w_bin_p.wsv:95-100`：

```火山
方法 取字节集右边 <公开 静态 类型 = 字节集类 注释 = "返回一个字节集,其中包含指定字节集中从右边算起指定数量的字节." @嵌入式方法 = "">
参数 所欲操作本对象 <类型 = 字节集类 注释 = "提供所欲操作的字节集对象">
参数 欲取出字节的数目 <类型 = 整数 注释 = "提供欲取出字节的数目,必须大于等于0.">
{
    @ @<所欲操作本对象>.GetBinRight (@<欲取出字节的数目>)
}
```

- 返回类型为 **`字节集类`** → 它**返回一个新字节集**，不是原地修改；
- 嵌入体是 `CVolMem::GetBinRight(n)` —— **纯取值访问器**，不修改接收者；
- 与该类库的原地修改方法命名区分明确（对照 `清空字节集(所欲操作本对象:字节集类)` 的注释"删除本字节集中的所有当前内容…本方法调用后,本字节集的长度将为0"）。

**后果**：`size > 读取大小` 分支每次都用 `内存复制` 从 `响应字节集` 的**开头**拷贝同一段 `读取大小` 字节，而 `响应字节集` 始终没有变短 → `size` 恒大于 `读取大小`，**永远进不到 `清空字节集`/`返回 (假)` 的终止路径**。任何超过 CEF 单次读取块（通常 8–32KB）的 `mcp://` 响应体将**重复输出首块**（数据损坏）或挂死。注册大数据（`browser_kernel_scheme` 的 `data`/`file`）必然触发。

**修复**：补上赋值 —— `响应字节集 = 取字节集右边 (响应字节集, size - 读取大小)`。

### 2.4 音频事件返回 `真` → 启用音频指纹 Hook 即**静音整站音频**


**类库契约（类库源码原文）** —— `资料/类库/FBroEventControl.wsv:1632-1637`：


### 3.14 `取安全主框架` 对"未被本线程持有"的 `MCP执行锁` 执行 `解锁()` —— 作者已注明这是未定义行为

**位置**：`src/MCP_Server.wsv:6900-6930`（关键行 **6917**），联动 `:2273-2300`、`:184`、`main.wsv:173`

```火山
     注释 = "调用方已持有MCP执行锁时默认真(延时期间放锁); 未持锁必须传假, 否则对未持有锁解锁是未定义行为"
```

**而调用点省略了该参数 → 走默认 `真`**（`MCP_Server.wsv:6914-6917`）：

```火山

{
    等待次数 = 等待次数 + 1
    MCP可中断延时 (200)          // ← 省略 是否持锁 → 默认 真 → 会执行 解锁/延时/加锁
    ...
}
```

`MCP可中断延时` 在 `是否持锁 = 真` 时执行 `MCP执行锁.解锁 () → 延时 () → MCP执行锁.加锁 ()`（`:2289-2294`）。

**不持锁的调用链（已逐环确认）**：

```
main.wsv:173  浏览器容器.恢复欢迎页 ()        ← 主循环 500ms 节拍 / UI 线程，不持有 MCP执行锁
  └─ MCP_Server.wsv:145 恢复欢迎页
       └─ 导航欢迎页内部 (:173)
            └─ :184  frame = MCP命令服务器.取安全主框架 (browser)
                 └─ :6917  MCP可中断延时 (200)   ← 对未持有的递归互斥锁执行 解锁()
```

**后果**：`取安全主框架` 的设计前提是"调用方已持 MCP执行锁"（Core 各分派调用方确实持锁，故放锁等待是正确的）；但上述 UI 线程路径不持锁。当主框架尚未有效时（欢迎页重建/布局恢复期间正是这种状态）会进入该循环，对**未被本线程持有**的递归互斥锁调用 `LeaveCriticalSection` 语义的解锁 —— 破坏递归计数与所有权，可能导致**互斥失效（两线程同时"持有"）或死锁**。

**修复**：该调用点传 `是否持锁 = 假`（与 `MCP_Server_Core.wsv:350` 的做法一致），或让 `取安全主框架` 显式感知自身是否持锁。

## 7. 值得关注的设计约束（非缺陷，但影响风险面）

1. **手写 JSON 拼接是全局风险点**：`MCP_Server.wsv:8573-8575` 记录 `L6: YYJSON对象类.加入成员/加入数组成员 嵌套多层会触发 0xC0000005, 工具列表/MCP响应一律用 文本拼接`。这使得 `JSON转义文本` 成为整个 MCP 协议正确性的单点 —— 已单独审计，**结论正确**（见 §5）。
2. **同一类参数读取缺陷可能成批复现**：§2.1 与 §3.2 都是"schema 声明的类型 ≠ 实现读取用的访问器"。作者已在 `yyjson取逻辑_默认` 中修好一类，但未全项目收敛。建议**新增参数读取统一走 `yyjson取逻辑_默认`/显式类型校验**，并加一条"schema 类型 vs 访问器"的静态检查。
3. **`MCP_Server_Core.wsv` 单方法 6800 行**是维护负担（无独立单元可测），但不构成语法或编译风险（§1.1）。
4. **协议合规设计到位**：`id` 类型保真（数字回数字、文本回文本，含 `id:0`）、无自定义扩展字段、`protocolVersion = 2025-06-18`（`MCP_Constants.wsv:66`）。
5. **工具数量单一来源良好**：`工具总数` 由 `完成构建工具列表` 动态写入（`MCP_Server.wsv:8602`），`/health` 上报该值 —— 与文档中"255 vs 265"的混乱形成对比（文档问题，非代码问题）。
